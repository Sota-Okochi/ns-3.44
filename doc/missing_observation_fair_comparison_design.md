# 欠測処理の共通化と公平な基地局選択比較：設計書

- 作成日：2026-10-10
- 状態：設計案。本文の v2 API・設定・ログは未実装。
- 対象：ns-3.44、AP0（5G）、AP1/AP2（Wi-Fi）。ログの基地局IDは0始まり。
- 今回の作業：既存コード調査と本書作成のみ。実験条件・モデル・シミュレータは変更しない。
- 関連：[DRL設計](drl_design_spec.md)、[AP0 logistic実験](ap0_capacity_logistic.md)。古い文書の閾値ではなく、以下に記載した現行コードを移行の起点とする。

## 1. 目的と範囲

「欠測するとlogisticだけが判断を停止する」「RLだけが真の容量や未来情報を使う」
といった差を取り除き、方策の違いを比較できる観測・評価基盤を作る。
共通化は全手法が同じ行動をすることではなく、同一状態なら同じ観測スナップショット、
欠測規約、評価式、実行制約を利用することを意味する。
方策が異なれば接続先と実測値は異なる。各手法に同一の数値を強制してはならない。

最初の対象は no_switch、random、ルールベース、logistic、最小RL。
RLの協調報酬、能動プローブ、容量予測は本設計と分離し、最初は追加しない。
欠測補完そのものを新規手法とは主張しない。

## 2. 現行実装で確認した問題

| 箇所 | 現行動作 | 問題 |
|---|---|---|
| `master/applications.cc::CollectTerminalThroughput` | FlowMonitorを集計。監視器や計測窓が不正なら早期return | 未到着・ゼロ受信・計測器不在の理由を上位で区別する必要がある |
| `APselection.cc::setTerminalTp` | 値を格納し `m_has_terminal_tp=true` | 到着済みというフラグと、値が正かという条件が混在 |
| `ResetMonitorStats` | 周期ごとにTP/RTT値・有効フラグを消去 | 履歴補完用の記録は別管理が必要 |
| `logistic_assignment` | 正のTPを持つ端末からAP平均TPを計算。1 APでも対象0台なら全体を接続維持 | 音声/ゲームだけのAPや空APができると推論が止まる |
| `calculate_satisfaction` | TPが欠測または非正なら0.1（猶予条件では別値） | 本当のゼロと欠測が混同される。0.1より低い実測満足度より欠測が有利になり得る |
| 同上 | RTT欠測/非正なら要求RTTで代用 | 情報がないのに満足度1相当になる |
| `WriteMasterLog` | `measurement_valid` はTPアプリで正のTPを要求 | 有効なゼロ計測を表現しにくい |

ソースは `contrib/kameda/model/server/APselection.{cc,h}`。
現行要求値はブラウザ3.0 Mbps、動画8.0 Mbps、音声100 ms、ゲーム40 ms。
研究メモのブラウザ2.3 Mbpsとは異なるため、移行では3.0を維持し設定・manifestへ保存する。
不満足判定は現行ログに合わせ S < 0.5。S < 1 の要求未達率も別に出す。
RTTは基地局の監視端末による代理値であり、個々の音声/ゲームフローの実測RTTではない。
logisticはアプリだけでなくAP人数・TP・RTTも入力している。方式自体が静的だとは扱わない。

## 3. 原則：生観測、方策入力、評価値を分離する

```text
計測器 -> RawObservation -> 共通ObservationBuilder -> PolicyObservation -> 方策
                 |                                         |
                 +-> 共通QoEEvaluator                       +-> 行動制約器 -> 切り替え
                 +-> 生観測ログ             評価/方策/行動ログをrun_idで結合
```

- 方策用に補完したTP/RTTを、実測QoEや報酬の実測値として使わない。
- 真の設定容量、未来の変更イベント、未観測の候補AP性能を入力しない。
- 観測TPは実現スループットであり、空き容量や最大容量の推定値とは呼ばない。
- 同じ欠測規約を、logistic、RL、ルールベースの特徴量生成にも適用する。
- 将来の教師データ作成で反実仮想の情報を使う場合も、実行時の入力とは隔離する。

## 4. 生観測の契約

値だけでなく、対象・計測窓・有効性・時刻を保存する。

| フィールド | 意味 |
|---|---|
| run_id, cycle_id, entity_type, entity_id, metric | UE/AP・TP/RTT等の識別 |
| window_start_sec, window_end_sec, received_at_sec | 測った時刻と受け取った時刻 |
| value, unit | 未観測値は空欄。0を欠測記号にしない |
| status | 下表の状態 |
| eligible_count, observed_count | AP集約対象数と観測済み数 |
| assignment_version | 計測時点の接続先状態 |

### 状態分類

| status | 例 | 処理 |
|---|---|---|
| observed | 正常なTP/RTT | 現在観測として利用 |
| observed_zero | 送信需要があり計測窓も正常だがTP=0 | 有効な品質悪化。欠測補完しない |
| not_applicable | 音声端末の動画用TP特徴量 | 適用対象外。障害と区別 |
| no_eligible_users | APにTP対象アプリがいない/空AP | AP平均TPは未定義。容量0ではない |
| missing | 来るはずの報告が来ない | 欠測補完対象 |
| invalid | NaN、負TP、非正RTTなど | 無効値として警告 |
| timeout | プローブを送信したが期限内に応答なし | 単なる計測器欠測と分け、品質障害として扱う |

ゼロ受信と「アプリが送信しなかった」を区別するため、需要/送信実行と観測窓の情報を追加する。
現行ログだけから区別できない場合は遡って分類しない。unknown理由付きで記録し、新規実験で計測を整える。
ブラウザの非送信区間を無条件に障害扱いしない。評価窓は既存の送信スケジュールに合わせる。
AP平均TPはTP対象アプリの有効観測（ゼロを含む）から作り、対象数と観測数を必ず併記。
アプリ構成に依存する値なので、ブラウザ/動画人数を一緒に公開する。

## 5. 方策用補完：v2の初期案

### 5.1 優先順位

1. 今周期の有効値。ゼロTPもそのまま使う。
2. 同じ対象・指標の期限内の直近有効値。
3. 学習用データのみで確定した固定prior（代表値）。

初期案は `max_stale_cycles=1` とする。最適値と断定せず、0/1/2周期で感度分析する。
時刻差も保存し、周期長が変わっても鮮度を解釈できるようにする。
履歴補完は観測の更新ではない。補完のたびに観測時刻を新しくしない。
エピソード間では履歴を消し、前runの結果を持ち越さない。
UEが切り替わったら旧APでのTPを新APの実測として再利用しない（別履歴としてのみ保持可能）。
APの人数・アプリ構成が変わった後の履歴は `composition_changed` を立て、不確かさを明示する。

### 5.2 入力の付随情報

全補完値に以下を付ける。
`observed_mask`, `applicable_mask`, `source={current,last_valid,prior}`,
`age_sec`, `age_known`, `eligible_count`, `observed_count`, `composition_changed`。
未知ageを0秒と同一視しない。数値には有限なプレースホルダーとマスクを組にして使う。
logisticもRLも同じ情報にアクセスできるようにする。
欠測が1 APにあるだけで全端末の推論を中止する処理は、v2方策経路から除去する。
モデル破損や観測スナップショット自体の不整合は別問題であり、理由をログにして接続維持する。

### 5.3 priorと正規化

- prior、scalerは学習分割のみから作成し、JSONに固定してhashを保存する。
- 評価runの平均、テスト期間の将来値から作らない。
- 方策間で同じprior/scalerと観測スキーマを使用する。
- アプリ/基地局別priorを使うなら、その区分と学習サンプル数を保存する。
- 学習データにも情報がない区分のfallback値は、実験開始前に設定し根拠を記載する。
- 補完値は容量推定の正解ではない。マスクなしで観測値と同等に扱わない。

## 6. 評価・報酬の欠測規約

### 6.1 実測評価を優先

完全な評価窓では S=TP/TP_need または RTT_need/RTT。
有効なTP=0では数学上H=0。逆数計算をせずゼロ分岐で算出し、分母0/NaNを防ぐ。
正のSが非常に小さくても0.1へ切り上げない。
RTT timeoutは設定した観測期限と送信記録で判定し、v2ではサービス失敗としてS=0とする。
RTTの単なる欠測はtimeoutと区別する。監視RTT失敗はAP単位の代理評価であることを注記する。

これは旧評価からの変更なので `qoe_schema_version=2` を付ける。
旧列の意味を黙って変更しない。v1再現モードとv2評価を別系列で保存する。
実装上すべてのSを正にする必要がある箇所ではepsilonを用いた別の数値表現を使えるが、
そのHを実測H=0と混同しない。epsilon値は設定に保存する。

### 6.2 評価データが本当に欠ける場合

- 実測全体Hは `h_observed_complete` とし、必要な評価値が欠ければ空欄。
- 全80端末という分母を維持した保守的スコア `h_conservative` を別途計算する。
  未観測の必要指標をS=0とするため、1台でも該当すればこのスコアは0になる。
  非負満足度に対する保守値であって、実測QoEではない。
- `evaluation_coverage`、欠測人数、欠測理由、不満足数の既知部分/不明部分を併記する。
- 有効端末だけのHは補助指標。欠測端末を除くことで勝てる指標を主評価にしない。
- 再実行/無効判定の基準を事前固定し、悪いQoEを理由にrunを除外しない。
  runを除外するなら同じシナリオの全比較手法を再実行し、失敗率も公開する。

v2最小RLの報酬案は `h_conservative - lambda * switch_count / N`。
欠測で報酬が悪化することも仕様として明記する。頻繁な計測欠測で全方策の報酬が0中心なら、
学習を本格化せず先に計測系を修正する。閾値・lambdaは学習側で固定してテスト中に調整しない。
過去値/priorで補完したQoEを報酬へ混入しない。

## 7. logisticの移行と公平性

既存 `logistic_model_v3.json` は旧11特徴量と旧scalerを前提とする。
マスク・鮮度を追加した値をそのまま既存モデルへ渡してはならない。

| 系列 | 用途 |
|---|---|
| logistic_legacy | 旧動作の再現。欠測で停止することもそのまま保存 |
| logistic_v2 | 共通補完・マスク・鮮度に対応して再学習。主比較対象 |
| reactive_rl_v2 | 同じ観測情報・制御条件から学習。主比較対象 |
| rulebase_v2/random/no_switch | 学習不要の比較。共通評価器・実行条件を使用 |

学習データ・教師ラベルの生成手順は `baseline_methods/` 内を改めて調査して対応箇所を決める。
旧入力で推論を続けるだけの応急処置は補助実験とし、新入力で学習済みRLとの主比較にしない。
教師モデルとRLの学習手順を同一にする必要はないが、学習シナリオ分割、利用可能情報、
評価予算・チューニング予算を明示する。モデル/学習データのhashを保存する。
履歴をRLだけに与える実験は「履歴の効果」の別比較であり、同情報量比較と呼ばない。

## 8. 観測以外の条件も揃える

- AP0容量、変動系列、配置、アプリ、トラフィック要求、測定窓、制御周期を一致させる。
- 乱数seedだけでなく、配置/アプリ/容量イベント用の乱数streamとrun番号を固定・記録する。
  方策の行動が異なると乱数消費も変わるので、同seedだけで全外乱が一致すると仮定しない。
- 実現した初期配列と容量イベント列を保存し、対になるrun同士で照合する。
- モデルに未来の容量イベント列を渡さない。解析専用ログに分離する。
- 最初は制御周期9.5秒、warmup3秒など既存設定を維持。周期短縮は別要因として検証。
- 切り替え上限・クールダウン・切り替え猶予・遅延を共通にする。
  現行logisticは `max_switches=8` のログでも60台変更できるため、上限表示だけでは不十分。
- 主比較v2の初期案はK=8。共通行動制約器が変更候補を現在満足度の低い順、同値はUE ID順で
  最大K台まで適用する。提案割当と実際の割当を両方保存する。
  この制約器も性能へ影響するため全手法で共通化し、Kの感度分析を行う。
- 不満足端末以外の移動を全方式で禁止しない。本人以外の改善に必要な可能性がある。
- no_switchの0変更は方式の定義。legacy無制限比較は別系列に分ける。
- 新規のTPプローブは初期段階で導入しない。将来使う場合は全方式で同一周期・負荷にする。

## 9. 時間対応とログ設計

周期tの観測 -> 方策入力 -> 行動a_t -> 実適用 -> 周期t+1の観測という対応を記録する。
Hの上昇は環境の容量回復でも起きるため、`H(t+1)-H(t)`を行動単独の因果効果と呼ばない。
終端の未評価行動を次周期の成功として数えない。

既存master CSVは互換性のため保存し、新規sidecarを追加する初期案とする。

| ログ | 必須内容 |
|---|---|
| observation_raw.csv | 第4節の生値、状態、時刻、窓、接続先バージョン |
| observation_policy.csv | rawへのキー、補完値、mask、source、age、schema version |
| decision_status.csv | cycle、policy_invoked、fallback_reason、model hash、提案/適用switch数 |
| evaluation_v2.csv | UEの必要指標状態、実測S、全体H、保守H、coverage、未観測数、不満足数 |
| action_trace.csv | action_cycle、UE、計測時AP、提案AP、適用AP、却下理由、適用時刻 |
| manifest.json | seed/run/stream、設定・ソース・モデルhash、観測/評価version、prior/scaler |

全ログにrun_idを付け、AP/UE ID規約と単位を統一する。
既存 `measurement_valid` はそのままにし、詳細は新ログへ保存。意味の変更にはversionを伴わせる。
解析コードも同時に更新し、v1/v2を混ぜた比較を拒否する。
`check_ap0_capacity.py` の容量イベント検証と、方策/観測検証は分ける。
`analyze_ap0_logistic_capacity.py` は現行v1解析として維持し、v2用の読み込みを別に追加する。

## 10. 実装順序と完了条件

### Phase A：診断ログのみ（実験条件を変えない）

- TPゼロ/欠測の生成経路、RTTプローブ送信・応答・timeout経路を追跡。
- `policy_invoked` とfallback理由、観測対象数を追加。
- AP2が音声/ゲームだけになる既存ケースで、停止原因をログから確定。
- 完了条件：同設定のlegacy結果がログ追加前と一致し、理由が追跡できる。

### Phase B：共通観測ビルダーと単体テスト

- RawObservation/PolicyObservationとschemaを定義し、方策から独立したモジュールを追加。
- 履歴、TTL、prior、maskを実装。legacy経路は残す。
- 完了条件：同じraw入力なら各アダプタへ渡る共通特徴量が一致。

### Phase C：v2評価器と解析

- ゼロ/欠測/timeoutを分離した評価器、sidecar、解析を実装。
- 評価式とパラメータを設定化し、v1結果を上書きしない。
- 完了条件：不正値で0除算せず、補完値が実測Hへ混入しない。

### Phase D：方策移行

- logistic_v2を再学習。RL実装前に推論が継続できることを検証。
- 共通行動制約器を導入し、上限の実適用を確認。
- 同観測契約で最小RLを接続。
- 完了条件：APのTP対象0台でもモデルが呼ばれ、提案/適用/翌周期の接続が追跡可能。
  「動く」とは推論すること。必ず切り替えることではない。

### Phase E：公平な実験

- seed1001、80端末、AP0 80->40->80と80->20->80、80一定で動作確認。
- legacy無制限とv2制限付きは混ぜない。容量一定logistic_v2も必ず含める。
- 本評価は別seed群、別変動系列、複数学習seedへ拡張。5周期は動作確認に留める。
- 平均H、下位H、要求未達/不満足数、アプリ別TP/RTT、切り替え回数、他端末悪化、
  計算時間、coverage、fallback率をseedごとに集計してばらつきを示す。
- 容量変動下の全体H改善は検証課題であり、本書の設計だけで達成を主張しない。

## 11. 必須テスト

1. 正TP、ゼロTP、負値、NaN、報告未到着が異なる状態になる。
2. 音声/ゲームのみAP、空AP、TP対象はいるが全員未計測を区別する。
3. 有効なゼロが過去の正値/priorで上書きされない。
4. TTLの境界、未知age、周期resetと履歴保持、run resetを検証。
5. UE切り替え後の旧AP実測を新APの現在値へ混入しない。
6. 欠測RTTを要求RTTで補って実測満足度1にしない。
7. 全員/一部ゼロでH=0、正常値で手計算のHと一致、欠測時はcoverageと保守Hが一致。
8. futureの観測や容量イベントを変更しても、現在までのPolicyObservationは変わらない。
9. 同一snapshotからlogistic/RLアダプタの共通部分が一致し、列順・単位も一致。
10. K超過候補の選別が決定的で、実際の切り替え数がK以下。接続維持も許可。
11. 一つのAPのTP欠測だけでpolicy_invoked=falseにならない（モデル正常時）。
12. v1/v2の混在、モデル入力schema/hashの不一致を実行前に検出。
13. 評価データからprior/scalerをfitしないことをデータ分割テストで確認。
14. 同seed/config/modelで再現性を確認。計算時間など非決定的な列は比較から分離。
