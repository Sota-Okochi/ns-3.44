# 局所観測に基づく協調型 MARL 基地局割り当て：設計案

作成日：2026-10-12

対象：ns-3.44、AP0=5G、AP1/AP2=Wi-Fi

状態：**設計案。MARL は未実装、学習・性能評価は未実行。アルゴリズムも未確定。**

## 1. 目的と合意事項

各端末が取得可能な限定的な情報から接続先を判断し、端末満足度の調和平均を通じて
全体 QoE を改善する。既存 DQN の拡張や MARL の採用自体を目的としない。
全端末の最新情報が中央に揃うまで待つ運用を避け、情報共有量と実装可能性も評価する。

| 項目 | 方針 |
|---|---|
| 初期端末数 | 80台 |
| 将来の評価 | 100台。通信形式・モデルを80台固定にしない |
| 主比較手法 | `no_switch`、`random`、`logistic` のみ |
| 主目的 | 全体の端末満足度の調和平均。平均TPや不満足端末数だけで判断しない |
| 同時切り替え | 初期版に切り替え数上限・待機期間・集中抑制器を必須導入しない |
| 学習方式 | DQNにもMAPPOにも固定せず、関連研究と実験コストから選定 |
| 公平性 | 計測・QoE規約の相違を調査し、変更案を提示してから修正 |
| 既存環境 | ns-3.44、既存手法・設定・checkpointを維持 |

多数接続でもRTTが大きく増えなかったという観察は、制約を先に追加しない理由として扱う。
ただし、それだけからTPや全体QoEの悪化も起きないとは結論しない。
接続先の偏り・切り替え回数・品質変化を記録し、問題が観測された場合に追加対策を提案する。

## 3. 意思決定の分散性

### 3.1 エージェントと情報境界（提案）

初期候補は **1 UE = 1エージェント**。全UEで方策パラメータを共有する。
UEごとに別モデルや別Pythonプロセスを必須にしない。
基地局単位のエージェント化は別案であり、初期案へ混在させない。

| 情報 | Actorでの利用案 | 取得経路・注意 |
|---|---|---|
| 自端末のアプリ要求・接続AP | 使用 | 端末自身が保持 |
| 自端末のTP | 使用候補 | 現行収集点から端末内測定への対応を確認する |
| RTT | 接続APの監視RTTを初期候補 | 現行値はUE個別RTTではない。APからの通知が必要 |
| 自端末満足度 | 使用候補 | 共通QoE規約から計算。欠測時の扱いも明示 |
| 各APの人数・監視RTT・観測平均TP | 最小限を選定 | APが集約し周期通知。平均TPを空き容量と呼ばない |
| RSSI/RSRP | 将来候補 | 必要な観測経路を確認・実装するまでは入力しない |
| 他UEの詳細状態、全体H | Actorでは使用しない | 学習用Critic・報酬・評価に限定 |
| 真の設定容量、将来イベント | 使用しない | 学習入力にも入れず、実験設定/評価用として隔離 |

AP通知は値、観測時刻、受信時刻、有効性、対象数を持つ。未知値は有限のプレースホルダーと
欠測マスクで表現し、ゼロTPと欠測を混同しない。通知間隔・有効期限は設定化する。
未接続APでの自端末のTP/RTTを、観測済みの事実として与えない。
現行コードが中央で持つ情報を単に切り出す場合は「局所観測の模擬」と明記する。

### 3.2 学習と運用の分離

集中学習・分散実行（CTDE）を有力な候補とするが、採用は未確定。

```text
学習：各UEの経験 + 学習専用の全体状態 -> learner -> 方策モデルを保存/配布
運用：自UEの観測 + 受信済みAP通知 -> 自UEの方策 -> 接続先要求
評価：実測ログ -> 全体H等（行動決定へ逆流させない）
```

学習時の経験集約と、運用時に全UEの情報収集を待つ制御は別物である。
運用時は他UEの観測欠落だけを理由に自UEの判断を停止しない。
AP通知の生成にも情報集約コストがあるため「通信不要」とは主張しない。
モデル配布は版番号付きで行い、初期評価では重みを固定する。運用中の継続学習は別課題とする。

### 3.3 段階別に主張できる範囲

1. **局所観測方策の機能検証**：中央PythonでUEごとの入力を分離して一括推論。
   共通周期で同期適用してもよいが、通信遅延や自律分散実装の検証とは呼ばない。
2. **分散実行の検証**：AP通知・端末側キャッシュ・判断イベントをns-3で表現し、
   他UEの応答待ちなしに判断する。通知の遅延/欠損/古さと制御通信量を計測する。
3. **非同期化の拡張**：必要なら端末ごとの判断時刻を導入。時間間隔、報酬集計、
   割引、通知順序を再定義する。同期学習の性能がそのまま維持されるとは仮定しない。

1のみで「実社会で動作する完全分散制御を実装した」とは記述しない。

## 4. 問題定式化と行動

UE数をN、基地局数を3とする協調型・部分観測の問題として扱う。
UE i は局所観測 o_i,t から a_i,t ∈ {0,1,2} を決定する。
現在のAPを選ぶことを接続維持とし、重複したSTOP行動は初期案では追加しない。
共同方策の初期候補は Π_i π_θ(a_i,t | o_i,t) であり、全割り当て3^N通りを列挙しない。
履歴を使うRNNは必要性を検証してから追加する。

切り替え上限、cooldown、推定Hに基づく安全フィルタは初期案に導入しない。
一方、範囲外ID、利用不可能な接続先、通信破損への検証は必須であり、混雑制約と区別する。
AP IDは外部schemaで0始まり、既存C++内部の1始まりとの変換を境界で検証する。
UE IDもschemaで基準を明記し、配列位置だけに依存しない。

## 5. 関連研究とアルゴリズム選定

以下は一次資料に基づく候補整理であり、本無線環境での性能保証ではない。

| 候補 | 関連研究の要点 | 本プロジェクトで確認する点 |
|---|---|---|
| MAPPO | PPOを協調型MARLへ適用し、集中型価値評価を利用する [R1] | 局所Actorと全体QoEの整合、on-policy経験収集時間 |
| IPPO | 局所価値関数を用いる独立PPO。SMACで有効性を報告 [R2] | 学習構成は単純だが、相互影響下の安定性と共有報酬の扱い |
| QMIX | 個別Qを単調な混合関数で全体Qへ統合し分散選択 [R3] | 経験再利用と、負荷の相互作用に対する単調分解の適合性 |

既存DQNがあることだけを採用理由にしない。MAPPOも現時点では最有力と断定しない。
候補選定では、必要な情報、サンプル効率、実時間、端末数依存、安定性、実装検証負担を比較する。
予備選定を行う場合は学習/validation条件で行い、最終testを選定に使わない。
候補アルゴリズムの予備比較は、主比較対象3手法を追加するという意味ではない。

引用した研究は一般的MARLの方法論であり、基地局選択への先行研究調査を完了したものではない。
**実装方式を確定する前に、異種無線のassociation/handoverを扱うMARLの一次論文を追加調査**し、
エージェント単位、実行時情報、報酬、通信仮定、端末数、評価指標を対照表にする。
標準アルゴリズムを採用すること自体を新規性とせず、情報制約下のQoE設計・評価との違いを記す。

## 6. 報酬と実測の時間対応

時点tで直前の測定窓から得たH_tを観測し、共同行動a_tを適用する。
次の測定窓の実測からH_{t+1}と報酬r_tを確定する。同じ観測値を切り替え後の実測と呼ばない。
推定割り当てHは診断用とし、初期MARLの実測報酬へ混ぜない。

報酬は未決定。次の2案を検討する。

```text
案A：r_t = H_{t+1}
案B：r_t = H_{t+1} - H_t
任意拡張：r_t -= alpha * switch_count_t / N
                   + beta * num_degraded_non_switched_t / N
```

案Aは期間を通じたQoE水準、案Bは改善量を強調する。
特に割引なしの差分報酬の総和は終端H−初期Hになるため、両者を同一目的とは扱わない。
切り替え・悪化ペナルティは必須にせず、初期候補では係数0とし採否を別途決める。
制約なしで動作する方策の挙動を先に確認する。係数と正規化規約はmanifestへ保存する。
非切り替え端末悪化数の定義、欠測を含む場合の扱いも共通評価規約として固定する。

初期案は全UEで同じ協調報酬を共有する。自端末満足度だけの報酬にはしない。
個々の寄与の識別が難しい点は限界であり、difference reward等を根拠なく追加しない。
容量変化などの外生要因も次周期Hに影響するため、H差分を切り替えの因果効果とは呼ばない。

## 7. 学習をどのように進めるか

### 7.1 共通フロー（提案）

1. 80台用設定、QoE規約、seed分割、観測schema、報酬を固定しmanifestを保存する。
2. ns-3で初期接続を生成し、最初の測定窓を完了する。
3. 各UEは局所観測から行動を決める。全体状態は学習用経路へ分離する。
4. ns-3が要求を適用し、要求行動・適用結果・理由・時刻を記録する。
5. 次の測定窓で報酬と次観測を確定し、遷移/軌跡を保存する。
6. 所定の環境step数またはepisode数を収集したら学習更新する。
7. validationで重み固定評価し、事前に決めた基準でcheckpointを選ぶ。
8. 未使用test seedで、3比較手法と最終評価する。

同一seedの繰り返しだけで一般性能を主張しない。環境seedとモデルseedを分離する。
80UEの1周期は「80個の独立な環境遷移」ではなく、相互作用する1共同環境stepである。
episode長・収集量・更新回数・学習時間は未決定で、ns-3の実測コストを確認して設定化する。

### 7.2 PPO系を採用した場合の具体案（条件付き）

共有Actorは局所観測から3行動の確率を出す。MAPPOならCriticは学習専用の全体状態を使い、
IPPOなら局所観測を使う。ActorへCriticの情報を混入させない。

```text
behavior policyの版を固定
  -> trajectory収集（obs, requested_action, old_log_prob, value,
                     reward, next_obs, terminated, truncated, mask, policy_version）
  -> 次状態の価値を用いてreturn/GAEを計算
  -> UEごとの確率比 exp(new_log_prob - old_log_prob) を計算
  -> PPO clipped objective + entropy項でActor更新
  -> returnへの価値損失でCritic更新
  -> 有限回のepoch更新後に新しいtrajectoryを収集
```

旧DQNのreplayから無期限に経験を再利用する方式にはしない。
同じ共同報酬をN回加算して目的の大きさを変えず、UE/time/batchの平均規約を固定する。
収集中の重み更新による版の混在は初期版で避ける。
学習率、clip幅、割引率、GAE係数、entropy係数、batch、epoch、勾配clip等は設定化する。

真の終端はbootstrapしない。時間制限による打ち切りは終了目的に応じたbootstrapを定義し、
失敗runと区別する。最終行動の後には最終観測を受け、未観測の報酬を0で捏造しない。
通信失敗・適用不一致・数値異常はログに残し、不正な軌跡を正常経験として更新しない。

要求と適用が異なる場合、適用行動でold_log_probだけを置き換えてはならない。
障害なら初期版は当該軌跡を隔離する。将来、受け入れ制御を環境に含めるなら、
「要求が方策行動、受け入れ結果が環境遷移」という契約で学習を設計し直す。

QMIX等を選んだ場合は本節のPPO更新を実装せず、共同遷移のreplay、target更新、
行動mask、混合ネットワークの契約を別途確定する。

### 7.3 評価

評価時はoptimizer・探索スケジュール・正規化統計を更新しない。
確率的方策をsampleするかargmaxにするか、同値時の選択、乱数seedも明示する。
学習時と実行時の行動規約差によるAP集中も検証対象とする。

## 8. 可変端末数と通信schema

新しいschemaは既存DQNと分離し、version、run_id、episode_id、cycle/decision_id、
sim_time、num_agents、num_aps、policy_versionを持つ。
端末ごとの `ue_id, observation, valid_mask, observation_time` と、
`ue_id, requested_bs_id, decision_id` の行動リストを対応付ける。
適用応答には `previous_bs_id, applied_bs_id, applied_time, status, reason` を含める。
ID重複、欠落、範囲外、古い応答、異なるrunへの応答を検出する。

一括リストは輸送上の最適化であり、Actorに全体状態を与える理由にはしない。
段階2では受信済み端末ごとに処理できるようにし、全N件の到着を必須条件にしない。
学習用critic_stateと実行用observationsは別フィールド/経路とし、推論APIへ前者を渡さない。
メッセージ長上限とtimeoutは設定化し、N=100でも検証する。

Actor入力にUE番号の80次元one-hotや全UE連結を使わない。
AP数3は本研究の前提で、Nとは分離する。人数特徴は実運用で取得可能な値と固定スケールを
初期候補とし、全体Nによる正規化を使うならNの取得方法と通知コストも明記する。
集中Criticを採用する場合は、可変長UEエンコーダ＋pooling/mask等を候補とする。
平均poolingだけでは人数情報が消えるため、学習側にはNや集計量を別途与える案を検討する。

80台で再学習、100台で再学習、80台モデルを100台へ転用は別実験として扱う。
最後の転用を行うかは未決定。100台での評価結果から80台モデルを選び直さない。

## 9. 比較手法の計算規約：確認事項と提案

現行 `APselection::tmain` は手法分岐の前に要求値と実測Hを計算している。
確認した範囲では3手法がそれぞれ別の満足度式を持つわけではない。
ただし、共通式自体の欠測規約とlogistic固有の判断停止に注意が必要である。

| 確認した現行挙動 | 比較への影響・提案 |
|---|---|
| `cal_traffic_request` はヘッダーの要求値を使用。ブラウザ3.0 Mbps（研究メモは2.3） | 勝手に2.3へ変更しない。採用値を確認して全手法のmanifestに保存 |
| TPは正の端末TPを利用。非正/欠測は `SATISFACTION_FLOOR`、猶予中は別値 | ゼロ品質と欠測が混ざる。分離案は承認後に共通実装 |
| RTTはAP監視RTT。欠測/非正なら要求値へ代用しS=1相当 | UE実測と呼ばない。欠測が有利になる可能性を報告 |
| Hは満足度に `MIN_SATISFACTION_THRESHOLD=1e-6` の下限を適用 | 全手法の式と下限を一致させて記録 |
| logisticはAPごとの正TP観測数が0なら全体を接続維持 | random/no_switchと異なる方策上のフォールバック。発生回数と理由を計測 |

生観測、方策入力、報酬/評価の計算を分離する。全手法の評価式を共通化しても、
no_switchやrandomにlogisticと同じ特徴量を強制する必要はない。
logisticの入力・欠測処理を変更すると既存モデルとの整合が変わるため、再学習と版分けが必要か確認する。

提案する進め方：まず現行規約を `legacy_v1` として固定し相違の発生頻度を調査する。
欠測/ゼロの分離等が必要なら、影響・移行案をユーザーへ提示してから実装し、
全手法を同じ新規約で再評価する。新MARLだけ評価規約を変えない。
旧モデルと新規約を混在させた結果を純粋な学習アルゴリズムの優劣と断定しない。
関連：[欠測処理と公平比較の既存設計](missing_observation_fair_comparison_design.md)。
同文書の全提案を自動採用するものではない。

## 10. ログ・評価指標・再現性

既存列名は維持し、新schemaは独立ログまたは後方互換の追加列とする。
基本ログにrun_id、環境seed、モデルseed、cycle、時刻、UE、接続前後AP、アプリ、
TP/RTT、満足度/分類、位置、取得可能なら電波品質、AP人数、H、不満足数、switch_flag、rewardを保存する。
未取得の位置/電波品質を実測値として埋めず、欠測と理由を明記する。

追加項目：観測/通知時刻とage、validity、要求/適用行動、適用失敗理由、モデル版、
報酬内訳、非切り替え端末悪化数、推論時間、制御通信bytes/messages、学習step/update数。
既存ログが新methodを出力対象とするか、最終周期も出力するかを実装時に確認する。

評価は次を含める。

- Hの時間推移・期間平均、満足度分布、不満足端末数、平均TP/RTT。
- 切り替え数、非切り替え端末の悪化数、AP別接続人数、欠測率。
- 学習実時間、環境step数、モデル推論時間、通信量/通知鮮度。
- 複数環境seed・モデルseed間のばらつき、平均と標準偏差/信頼区間。

信頼区間の標本単位をrun/seedとし、相関したUE×cycleを独立標本とみなさない。
同じ初期条件・外生イベント・計測窓で比較し、方策で変わる観測まで同じに強制しない。
制御通信を無線へ流す実験ではその負荷を含め、中央TCPのbytesを無線負荷と呼ばない。
規模評価では総負荷/アプリ構成を明記し、人数増による負荷増と計算量増を区別する。

設定、ソース版/hash、依存バージョン、モデル/scaler、seed、イベント列、失敗runも保存する。
新外部依存は理由・導入手順を文書化する。再現用設定を共有の既定設定へ上書きしない。

## 11. 実装単位と検証計画

将来の追加候補は `rl/marl/` 配下のprotocol、observation、policy、learner、train、evaluateと、
ns-3側の新割り当て入口・観測adapter。名前とmethod名は未確定で、現時点の実行コマンドではない。
アルゴリズムが決まる前に `method=mappo` と固定しない。

1. **仕様確定**：関連研究比較、観測の実取得経路、報酬、QoE規約、学習方式を決める。
2. **最小接続**：少数UEで行動リスト、適用確認、次周期報酬、終端をテスト。
3. **80台評価**：局所観測方策を学習し、3手法と複数seedで比較。
4. **分散通信・100台拡張**：通知と判断の独立性、遅延/欠損、可変Nを検証。

必須テスト：

- 80/100台のshape、ID変換、UE並べ替えに対する対応、checkpoint schemaの検証。
- 同じ局所観測で他UE情報だけを変えてもActor出力が変わらないこと。
- 端末Aの欠測が無関係な端末Bの推論停止を招かないこと（分散段階）。
- 要求/適用一致、不正応答拒否、次観測との時間対応、最終報酬欠落の検出。
- 共通QoEのアプリ式、欠測、下限、閾値、ゼロ除算防止。
- PPOなら確率比、mask、GAE、terminated/truncated、評価時更新禁止。
- 同じ設定・seedでの再現性と、no_switch/random/logisticの回帰確認。

実行中実験とポート、モデル保存先、設定、ログ、必要ならビルド先を分離する。
利用中のPythonファイルやモデル、共有バイナリを上書きして実験に介入しない。
