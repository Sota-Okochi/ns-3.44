# 5G↔Wi-Fi 擬似ハンドオーバ設計書

## 1. 目的
- `--nth=5` の割り当て結果（`assignment`）を、実ネットワーク挙動に反映する。
- 連続シミュレーション中に、サイクル境界で `5G(AP0)` と `Wi-Fi(AP1/2...)` の接続先を擬似的に切り替える。
- 「無停止の真のインターRATハンドオーバ」ではなく、短時間断を許容した実装とする。

## 2. 現状整理
- `HandleHandoverRequest()` は `m_termData[i].apNo` と `m_apSelectionInput.initialAp` を更新するのみで、実デバイスやルーティングは変更していない。
- 端末のデバイス構成・IP・デフォルトルート・アプリ宛先は初期化時に固定化される。
- AP0はNR/EPC経路、AP1/2はWi-Fi+Router経路で、経路構成が異なる。

## 3. 方針（擬似切替）
- 切替タイミングをサイクル境界に限定する。
- 切替処理は次の順序で実施する。
1. 新しい割り当てを受領
2. 切替対象端末を抽出
3. 旧アプリ停止（短時間断）
4. 端末の有効経路（RAT/ルート）を切替
5. 必要に応じてIP再設定
6. 新アプリ再起動
7. 計測再開
- 切替中の一時的な損失・再送・RTTスパイクは設計上許容する。

## 4. なぜ難しいか（技術的論点）
- RATごとにアクセス方式と制御APIが異なる。
  - NR: gNB/UEデバイス + EPC経路
  - Wi-Fi: AP/STA + 静的ルーティング
- 端末が両RATを同時に持っていないと、RAT跨ぎ切替が不可能。
- IPアドレス空間がRATで分かれており、切替時にIP継続性が崩れる。
- 既存アプリは開始時に宛先/送信先IPを固定するため、経路切替だけでは追従しない。
- 計測値（TP/RTT）は切替瞬間の影響を強く受けるため、ウィンドウ境界設計が必要。

## 5. 対象範囲
- 対象: `--nth=5` のサイクル境界切替。
- 非対象:
  - 真のmake-before-break
  - L4セッション継続を保証するモビリティアンカー実装
  - RRC/ANDSF/ATSSS相当の高度制御

## 6. アーキテクチャ変更案

### 6.1 端末のマルチRAT化
- 各端末に「NRデバイス」と「Wi-Fiデバイス候補」を事前配備する。
- 1時点でアクティブに使うRATを1つ決める。
- 非アクティブ側はルート非優先化またはアプリ停止で実質無効化する。

### 6.2 接続状態管理
- `TermAccessState`（新規構造体）を導入し、端末ごとに以下を保持。
  - `currentAp`
  - `currentRat` (`NR`/`WIFI`)
  - `nrIpv4`, `wifiIpv4`
  - `lastSwitchTime`
  - `switchInProgress`

### 6.3 切替オーケストレータ
- `handover.cc` 側に切替実行関数を追加する設計とする。
- `HandleHandoverRequest()` は「配列反映」だけでなく、差分を作って切替キューを作成する。
- サイクル境界で `ExecutePseudoHandoverBatch()` を起動する。

## 7. 切替シーケンス詳細

### 7.1 差分抽出
- `assignment[i] != currentAp[i]` を切替対象にする。
- 同AP/同RATはスキップ。

### 7.2 事前停止
- 対象端末のTP系アプリ（動画/ブラウザ）を停止。
- 測定器は停止せず、切替中フラグを立てて集計から除外可能にする。

### 7.3 RAT切替処理
- `NR -> Wi-Fi`
  - Wi-Fi側のデフォルトルート有効化。
  - NR側デフォルトルートを非優先化。
- `Wi-Fi -> NR`
  - NR側デフォルトルート有効化。
  - Wi-Fi側デフォルトルートを非優先化。
- 同RAT内（Wi-Fi AP間）切替
  - AP再関連付け（または端末側経路再選択）を実施。
  - 必要に応じてAPサブネットのデフォルトルート更新。

### 7.4 アプリ再起動
- 端末の有効IP（新しいprimary）を再取得。
- サーバ側送信アプリ（例: `UdpTraceClientHelper`）を端末新IP向けに再生成。
- 端末側 `PacketSink` と対になるポートを再確保して再起動。

### 7.5 計測再開
- 切替完了後にFlowMonitor統計をリセット。
- サイクル計測窓を再開。

## 8. IP/ルーティング設計
- 端末は `NR用IP` と `Wi-Fi用IP` を持つ想定。
- 同一RAT内切替でIP維持できない場合は、切替時に新IPへ再バインドする。
- `GetPrimaryIpv4()` 依存実装は、切替後IPを確実に返すよう優先IFを制御する。

## 9. ログ設計（追加）
- `OUTPUT/handover-events.csv` を新規出力する設計。
- カラム例:
  - `time_s`
  - `term_id`
  - `old_ap`
  - `new_ap`
  - `old_rat`
  - `new_rat`
  - `old_ip`
  - `new_ip`
  - `downtime_ms`
  - `result`

## 10. 失敗時の扱い
- 切替失敗時はロールバックして旧経路維持。
- 失敗端末はそのサイクルでは再試行しない。
- ログに失敗理由（`ROUTE_UPDATE_FAIL`, `APP_REBIND_FAIL` など）を記録。

## 11. 実装ステップ（段階導入）
1. `phase-1`: Wi-Fi内擬似切替のみ実装
2. `phase-2`: NR内（gNB間）切替を追加
3. `phase-3`: NR↔Wi-Fi切替（アプリ再起動込み）を追加
4. `phase-4`: 計測系の除外窓・平滑化調整

## 12. 検証計画
- 機能検証
  - サイクル境界で割当差分数と切替イベント数が一致する。
  - 切替後に `master_log.csv` のAP列と実フロー宛先ネットワークが一致する。
- 品質検証
  - 切替直後に短時間断が発生し、その後TPが回復する。
  - RTT/TPが切替前後でAP特性に応じて変動する。
- 回帰検証
  - `--nth=4` 挙動を壊さない。
  - 切替無効フラグ時は現行と同一挙動。

## 13. オープン項目
- AP0/NRのgNBを複数化するか（将来のNR内HOのため）。
- 切替中トラフィックを「破棄」か「バッファ」か。
- 切替ダウンタイムの上限要求（例: 200ms, 500ms）。

## 14. 結論
- 擬似切替（サイクル境界 + 経路切替 + アプリ再起動）は実装可能。
- ただしインターRATの本質的課題は `IP継続性` と `アプリ再バインド` であり、ここを設計上の主対象とする。
