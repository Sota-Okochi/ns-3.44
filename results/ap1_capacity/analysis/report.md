# AP1容量変動分析（80端末・seed 1001）

## データ確認

両条件のmaster_logは各400行（80端末×5周期）。同じ初期端末・アプリ構成、
全周期で接続固定、切り替えゼロ、seed 1001を確認。
AP1はmaster_logのcurrent_bs_id=1（1始まりのIDでは2）。
変更イベントは両方向とも13.5秒に40→20 Mbps、32.5秒に20→40 Mbps。
AP1接続22台の内訳はブラウザ0、動画8、音声6、ゲーム8。全AP1行はmeasurement_valid=1。
5Gは21台、AP2は37台。AP1以外の端末のTP/RTT/満足度は全周期で条件間一致。

注意：queue_samples.csv末尾には両条件とも途中までの行がある。
constantの完全行は45.0秒まで、variableは52.2秒まで。
master_logの5周期分は揃っているが、これだけでプロセスの正常終了は断定しない。
バッファ未フラッシュ、コピー、途中停止等の原因は未特定。
解析では不完全行を除外し、constantのcycle 5キュー集計にはcomplete_cycle=Falseを付けた。
その周期のキューを完全周期の値として比較しない。

## 低下期間（cycle 2・3）の同周期比較

値は端末平均を各周期で計算し、その2周期を等重みで平均したもの。
動画TPは一定4.641→変動2.411 Mbps（-48.0%）、平均満足度0.580→0.301。
動画8台は一定条件で全員S>=0.5、変動条件では全員S<0.5。
ただし一定条件でも要求8 Mbpsは満たしていない。
動画8台の合計TPは変動中約19.29 Mbps。20 Mbps設定と整合的だが、
アプリTPの合計はリンク利用率そのものではない。

RTTは一定90.500→変動138.917 ms（+53.5%）。
音声は平均満足度1.105→0.720（-34.9%）、要求100 msを超過するがS<0.5ではない。
ゲームは0.442→0.288（-34.9%）、8台とも元から不満足であり、分類数には悪化が現れない。
AP1調和平均の2周期平均は0.5892→0.3511（-40.4%）。
回復後cycle 5の動画TPは一定4.504、変動4.495 Mbpsでほぼ一致。
RTTは一定79.833、変動79.333 ms。容量低下前cycle 1だけでなく同周期基準で回復を評価する。

## 解釈上の制約（ソース確認）

- rtt_msはAPごとの検査用端末のRTTを共有している。音声・ゲーム各端末の
  実アプリRTTを直接測った値ではなく、満足度もこの代理指標に基づく。
- 音声・ゲームのtp_mbps=0を通信停止と解釈しない。
- 現在の不満足閾値はS<0.5。要求未達S<1とは異なる。
  ゲームのcycle 5のS=0.504は分類上不満足ではないが、要求40 msは満たしていない。
- 現行コードのブラウザ要求TPは3.0 Mbps（研究説明の2.3 Mbpsとは相違）。
  今回AP1にはブラウザがいないためブラウザについて容量変動の影響は評価できない。
- TPが無効な場合の満足度代替値0.1が存在する。AP1には該当端末なし。
  AP2には毎周期1台measurement_valid=0があり、全体Hはログ定義に従って集計。
- 単一seedの固定接続実験。DRLや切り替えによる改善を示す結果ではない。

## 再現

実行コマンド:

```bash
python3 scripts/analyze_ap1_capacity.py --root results/ap1_capacity --output results/ap1_capacity/analysis
```

スクリプトは入力を変更せず、CSV4種と入力SHA256付きmanifest.jsonを出力。
by_bs_app_cycle.csvのapp_type=0は基地局全端末。n=0は未観測群で、ゼロ性能ではない。
元CSVの丸め済み満足度から再計算するためHは元ログと微小差が生じる。

次の検証: (1)ログ終了処理/回収の確認、(2)ブラウザも含む初期割り当てと複数seed、
(3)同じ外生変動で切り替えbaselineを比較し対象外端末への効果も測定。
