# 100端末 random / seed1001 キュー診断分析

## 入力と範囲

- `OUTPUT/100/random/queue_diagnostics/random_seed1001_1791548462319771_pid179524/queues.csv`
- 同ディレクトリの metadata.txt / setting.json
- `OUTPUT/100/random/master_log_1001_20261009_212102.csv`
- run timestampとmasterファイル名はいずれも2026-10-09 21:21:02 JSTに対応。
- 診断106300行、0〜51.6秒、0.1秒間隔。masterは5サイクル×100行。
- 設定JSONのseed=1002はCLIで1001に上書き。実際のseedはmetadataとCSVの1001を使用。
- 正常終了の標準出力は入力に含まれず、5サイクル記録済みという範囲で評価。

## 実行・集計方法

実行済みコマンド:

```bash
python3 scripts/summarize_queue_diagnostics.py OUTPUT/100/random/queue_diagnostics/random_seed1001_1791548462319771_pid179524/queues.csv --output results/queue_analysis_seed1001_20261010/queue_summary.csv
```

追加のPython標準csv集計で `cycle_summary.csv` を生成。
サイクルkの基準時刻は4+9.5*(k-1)秒、監視窓はその+1.1〜+6.0秒（両端を含む）。
queue mean/peakはその窓のDLサンプルから算出、RLC HOLは全DLベアラの最大。
monitor_rlcはue_id=-1のみ。破棄差分は窓末の累積値−窓開始直前サンプルの累積値。
masterのRTTは窓全体平均ではなく、監視端末側の直近最大6応答の平均に基づく。
cycle_window_idからmasterの判定時刻を直接推定せず、保存設定から監視窓を構成した。

## 解釈

今回の強いボトルネック候補は80 MbpsのPGW–CER下り、とくに上位QueueDisc。
前回の「約1GB RLCバッファの滞留が主因かもしれない」という仮説は、今回の観測では支持されない。
10.76MBを80Mbpsで排出する時間は約1.076秒。ただしこれは総量の排出時間であって
監視パケット個別の待ち時間やRTTの実測値ではない。

cycle4/5では総QueueDisc滞留が残っていても監視RTTは約102ms。
総量と個別フローの遅延の一対一対応は不可。現在のソースではIPv4アドレス付与時の
デフォルトQueueDiscはFqCoDel。診断CSVには型と破棄理由を記録していないため、
187795パケット全てを「上限超過による破棄」と呼んではいけない。
AQM等を含む内訳は未確認。サンプル間の短い滞留も未観測。

## 次の検証

1. 同じseed/設定/割り当て条件でPGW–CER帯域のみ80→120 Mbpsに変更した比較。
   必要なら160 Mbpsも追加。伝搬遅延と両キュー上限は変更しない。
2. 帯域増強でRLC側へ混雑が移らないか、同じ診断を継続。
3. seed1002等でも再現確認し、調和平均・不満足端末数・RTT・破棄数を比較。

キュー拡大は提案しない。80Mbps制約を研究条件として維持するなら、キュー制御の比較は
別実験として行う。100端末を快適に収容させることと、混雑回避方策を評価することを区別する。
本分析では設定・シミュレーションコード変更なし、追加シミュレーション未実行。
