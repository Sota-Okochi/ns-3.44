# 80/100端末 × 80/120/160 Mbps × seed1001/1002 分析

## 結論

今回の範囲では「80台は余裕があり100台は混雑」という領域に到達していない。
160MbpsでもAP0下りデバイスキューはほぼ常時600パケットで、監視RTTの端末数差は小さい。
帯域増加に伴ってRTT・動画TP・調和平均は改善するが、100台のRTTが80台を常に上回る傾向はない。
前の120/160Mbps候補は探索値であり、今回の結果から不足していたと判定する。

## 入力の監査

- manual_OUTPUTの12条件を使用。各masterログは5サイクル×端末数の行数、UE ID重複なし。
- 対応診断は全て56.5秒（保存設定の停止予定時刻）まで記録。
- masterファイル名と診断run_idの起動時刻を照合（差2秒未満）。
- 途中停止の診断2件（80台seed1001/80Mbpsの2.1秒まで、100台seed1001/80Mbpsの0秒のみ）は除外。
- 固定アプリ比率、速度、600p、20ms、QueueDisc10240p、RLC999999999Bを実ログで検証。
- 同一seed/端末数の帯域間で初期割り当てとアプリ列が一致。
- 80台は100台の先頭80台と初期割り当て・アプリ列が一致。
- 詳細パスと除外対象はaudit.json。

## 集計の定義

初期割り当てのcycle1を除きcycle2〜5を比較。各seed内で4サイクルを算術平均し、
2seedを等重みで平均。Hは各サイクルのHの平均であり、全サンプルを再プールしたHではない。
標準偏差は2seedのサイクル平均間の標本標準偏差（サイクルを独立seedとして扱わない）。
キューと流入量は各サイクルの監視窓 `[4+9.5*(k-1)+1.1, 4+9.5*(k-1)+6.0)` を用いる。
流入量は窓両端の累積バイト差分を時間で割る。IP層の量でPPPヘッダは含まない。
満杯率は0.1秒サンプル中で600pだった割合。連続時間の厳密な割合ではない。

## 解釈

### 容量はまだ不足

監視窓のAP0実流入は約232/249Mbps。最大比較帯域160Mbpsより大きい。
動画端末は80台条件で32台、100台条件で40台。動画TPはほぼ帯域をこの台数で割った値。
受信TPでは見えなかった入力側の過負荷が明らかになった。
流入量はバックホール入口の実測であり、上流の破棄前の全アプリ生成量ではない。

### 113msから91ms・81msへ移っただけ

満杯FIFOの待ちは概ねqueue_bytes*8/rate。動画のみなら632400bytesを送る時間は
80Mbps=63.24ms、120Mbps=42.16ms、160Mbps=31.62ms。
低負荷RTT約50msと合わせると今回の変化の規模と整合するが、個別pingの厳密な遅延分解ではない。
RLCの周期内最大HOLは小さく、周期2以降に大きな無線送信待ちは見られない（cycles.csv参照）。

### 損失と品質には差がある

QueueDiscの窓内破棄数/同窓流入数の比率（サイクル・seed平均）は
80Mbps=64.4%/67.3%、120Mbps=48.0%/51.3%、160Mbps=31.0%/35.2%（80台/100台）。
これはエンドツーエンド損失率ではない。窓開始前に受け入れたパケットの破棄も含み得る。
RTTがほぼ同じでも100台条件は1端末TPとHが低下し、混雑の影響が出ている。

### 方策の割り当ては帯域で変化している

80/120MbpsではAP0に動画のみ。160Mbpsではseed1001に限り音声もAP0へ移る。
80台では動画32+音声12=44台、100台では動画40+音声15=55台。
seed1002の160MbpsではAP0に動画のみ。
従って帯域以外の外生条件は固定していても、方策が選ぶ割り当ては固定していない。
160MbpsのHのseed差や不満足数差を帯域だけの直接効果と解釈しない。

## 次の検証案（未実行）

- 現在の入力から240Mbps付近を探索候補にする。例えば200/240/280Mbps。
  240Mbpsは今回の平均入力約232と249の間にあるが、入力はバースト的かつ方策依存であり、
  RTT差が出る保証や最適値の推定ではない。
- 純粋な待ち行列の比較には、AP0=動画・AP1=ブラウザ・AP2=音声/ゲームの固定割り当てを
  別シナリオとして用意する。logisticの方策込み評価は今回と同様に別途維持。
- バックホールに余裕を作ってもFqCoDelがping遅延を保護し得るため、差が出なければ
  それ自体を結果として扱う。ping損失と各アプリの品質も見る。キュー拡大や遅延の人工加算はしない。
